TransforM Egypt — Admin Dashboard Expansion. Current state: /admin route exists with ADMIN_TOKEN auth, currently displays Lucky-spin leads with CSV export. Goal: expand /admin into a full back-office system that captures all website form submissions and supports multi-user access for management, branches, and social media team. PHASE 1 — DATA SOURCES: Add form submissions from every public-facing form on transform-egypt.com to flow into the admin. Each submission becomes a record in a unified leads/bookings table. Forms to capture: Book Your Experience (main booking CTA), Free Consultation request, Gift Card purchase, Contact/general inquiry, Boutique product order, Newsletter signup. Each record should include: timestamp, source form, full name, phone, email, branch preference (if applicable), service requested, message/notes, language (EN/AR), status (default: New), and a unique submission ID. Database: use Replit Postgres or Supabase, whichever the existing /admin already uses. Do not migrate existing Lucky-spin data — keep that table, add new tables alongside. PHASE 2 — MANUAL ENTRY: Add a “Log New Lead” button in /admin that opens a form for staff to manually enter walk-ins, phone bookings, Instagram DM leads, and Facebook leads. Same fields as website forms, plus a “source” dropdown (Walk-in, Phone, Instagram DM, Facebook DM, Referral, Other). The logged-in user’s name should auto-attach as “logged by”. PHASE 3 — MULTI-USER AUTH: Replace the single ADMIN_TOKEN system with proper user accounts. Build a users table with: email, hashed password (bcrypt), full name, role, branch_assignment (nullable), created_at, last_login. Roles to support: Owner (sees everything across all branches, can add/remove users, sees revenue), Manager (sees everything for their assigned branch, sees revenue for their branch only), Receptionist (sees their branch bookings and clients, no revenue visibility), Social (sees only leads pipeline + website inquiries from all branches, can manually log Instagram/Facebook leads, no branch ops visibility). Login page at /admin/login with email + password. Session-based auth with secure HTTP-only cookies, 12-hour expiry. Add a /admin/users page (Owner-only) to create/edit/disable users. Keep ADMIN_TOKEN as a backup superuser bypass during migration but log a warning when used. PHASE 4 — DASHBOARD: Replace the current Lucky-spin-only view with a unified dashboard. Top of page: stat cards showing today’s bookings, this week’s bookings, new leads pending follow-up, total clients in database. Below: tabbed view — Bookings, Leads, Clients, Reports. Bookings tab: filterable table by branch / date range / status / source form, with columns name/phone/service/branch/status/date/source. Click a row to expand details. Status workflow dropdown: New → Contacted → Booked → Completed → No-show → Cancelled. Leads tab: same filters, focused on prospects who haven’t booked yet. Clients tab: deduplicated by phone number, shows client name, total bookings, last visit, lifetime spend (placeholder if revenue not tracked yet), preferred branch. Reports tab: charts showing bookings per branch (bar), bookings per source (pie), bookings over time (line), top services. Use Recharts since it’s already in the React stack. PHASE 5 — BRANCH FILTERING: When a Manager or Receptionist logs in, all queries automatically filter to their assigned branch. Owner and Social see all branches by default with an optional branch filter dropdown. Hard enforce this on the backend — never trust the frontend to filter. PHASE 6 — POLISH: Match the admin UI to TransforM brand (champagne gold #D4B97A primary, dark theme, serif headlines, sans-serif body). Mobile-responsive — receptionists will check this on their phones at the front desk. Add CSV export to every table view. Add a search bar at the top that searches across name, phone, email, notes. CONSTRAINTS: Do not break the existing /admin Lucky-spin functionality during migration. Build new features alongside, deprecate old single-token auth only after multi-user is fully tested. Keep the existing E2E test pattern — write new tests for each new feature. Use bcrypt for password hashing, never store plain passwords. All API endpoints must verify session and role on every request, not just on initial login. Add basic rate limiting on the login endpoint (5 attempts per 15 minutes per IP) to prevent brute force. REPORTING: Before deploying to production, produce a summary of: new database tables created, new routes added, role permission matrix (which role can access which route/action), and any security considerations the user should know. Deploy to a preview environment first for testing.
